# AI Context for PixelLust Template and PixelVoxelPuzzle

Last updated: 2026-06-14
Purpose: one navigation file for AI agents working in this Unity project. Use this as a fast map of Template modules, managers, scenes, setup flow, PixelVoxelPuzzle runtime architecture, and important file locations.

Important rule for AI work:
- The generic Template lives under `Assets/Template`.
- The game-specific PixelVoxelPuzzle implementation lives under `Assets`.
- Do not put puzzle-specific rules into generic Template modules unless the user explicitly asks for a reusable Template change.
- Prefer project-side bridge components when connecting PixelVoxelPuzzle to generic systems.
- Several docs describe future/planned systems. Current code is the source of truth when docs disagree.

## 2. Template Setup Principle

Template is intended as a Unity submodule mounted at:
- `Assets/Template`

Setup script:
- `Assets/Template/setup.bat`

What `setup.bat` does:
- Warns that it overwrites project settings and waits for Enter.
- Copies `.Sync/Settings` to `Assets/Settings`.
- Copies `.Sync/AddressableAssetsData` to `Assets/AddressableAssetsData`.
- Copies `.Sync/ProjectSettings/*.asset` to `ProjectSettings`.
- Merges/syncs `Packages/manifest.json` through `.Sync/sync_manifest.ps1`.
- Copies `.Sync/Packages/packages-lock.json` to `Packages/packages-lock.json`.
- Copies template gitignore data to the project-side target path used by the script.

Use setup when initializing or resyncing a project from Template. It is destructive to local settings, so do not run it casually in an AI task unless the user asks.

Important Template file paths:
- `Assets/Template/ImportantFilepaths.cs`
  - `KeysConfigPath`: persistent `config/controls.cfg`
  - `SettingsConfigPath`: persistent `config/config.cfg`
  - `MainSavefilePath`: persistent `saves/save.cfg`
  - `SavesFolderPath`: persistent `saves/`
  - cloud paths for controls/settings configs

Current package highlights from `Packages/manifest.json`:
- Cinemachine `com.unity.cinemachine`
- Addressables `com.unity.addressables`
- Unity Localization `com.unity.localization`
- Unity Input System `com.unity.inputsystem`
- URP `com.unity.render-pipelines.universal`
- Netcode for GameObjects `com.unity.netcode.gameobjects`
- DOTween is vendored under `Assets/Template/Plugins/DOTween`
- Odin/Sirenix is vendored under `Assets/Template/Plugins/Sirenix`

## 4. Template Manager Pattern

Base class:
- `Assets/Template/Managers/Manager.cs`

Pattern:
- Most managers inherit `SingletonManager<T>`.
- Singleton managers expose static `Instance`.
- They also expose `Promise` through `DanieloZ.InstancePromise.InstancePromise<T>` for async/lazy access.
- Duplicate singleton objects destroy themselves in `Awake`.
- Use `[M]` in GameObject names for manager objects.

Network variant:
- `SingletonNetworkManager<T>` for Netcode `NetworkBehaviour` managers.

Guideline:
- If a manager already exists in Main, Game-scene systems should reference/use it. Do not create a duplicate manager in Game unless it is a scene-specific bridge.

### DanieloZ.ScreenSpaceOutline

Path:
- `Assets/Template/Modules/DanieloZ.ScreenSpaceOutline`

README:
- `Assets/Template/Modules/DanieloZ.ScreenSpaceOutline/README.md`

Purpose:
- Reusable URP RenderGraph screen-space outline rendering.
- Selects outlined renderers through a layer mask.
- Supports visible outlines, occluded outlines, solid-color occluded silhouettes and an optional mix with the object's front-most rendered visual.
- Multiple feature instances may use different layer masks and material profiles, but each instance adds rendering cost.

Core files/assets:
- `Runtime/ScreenSpaceOutlineMaskFeature.cs`
  - Renders visible and occluded masks, optional object visual, and the final composite.
  - Remains in `Assembly-CSharp`; do not add an asmdef without migrating serialized Renderer Feature instances.
- `Shaders/MaskShader.shader`
  - Visible mask.
- `Shaders/OutlineOccludedMask.shader`
  - Occluded mask.
- `Shaders/ScreenSpaceOutlineComposite.shader`
  - Outline and silhouette composite.
- `Materials/WithTexture`
  - Material profile that renders and mixes the selected object's visual into the occluded silhouette.
- `Materials/WithoutTexture`
  - Solid-color silhouette profile that skips the object-visual pass.

PixelVoxelPuzzle renderer setup:
- `ScreenSpaceOutlineMaskFeatureWithTexture` targets `PuzzlePieceSelect`.
- `ScreenSpaceOutlineMaskFeatureWithoutTexture` targets the remaining outline layers.
- Project-side selection components switch renderer layers; outline rendering itself stays generic in Template.

## 8. PixelVoxelPuzzle Project Layer

Root:
- `Assets`

Major folders:
- `Runtime`
- `Editor`
- `Materials`
- `ScriptableObjects`
- `Prefabs`
- `Generated`

High-level architecture:
- Template managers provide global app services.
- PixelVoxelPuzzle Game scene provides scene-specific systems under `Systems`.
- The active runtime puzzle is spawned/controlled under `Runtime/ActivePuzzleSession`.

Current source-of-truth runtime path:
- `Puzzle*` classes under `Assets/Runtime/Puzzle`
- `Hand*` classes under `Runtime/Hand`
- input contexts under `Runtime/Input`
- project UI modules under `Runtime/UI`

Do not treat old names as current:
- Current placement runtime uses `BoardAreaController`, `PuzzlePlacementArea`, `PuzzlePiece`, `PuzzlePieceHoldable`, `PuzzlePlacementService`, `PuzzleSessionFactory`, `PuzzleSessionManager`, `PuzzleCompletionService` and `PuzzleCompletionHandler`.

`PuzzleBoxController.cs`
- Root controller for a puzzle box.
- `BoxShrinkSource = "PuzzleBox"`.
- Auto-wires expected child names through `AutoWire`.
- Auto-wires both canonical `[TRIGGER]` / `[COLLIDER]` helper names and old unprefixed names so old generated prefabs keep working until rebake.
- Controls open/closed state through animator/open parameter.
- Tracks outside/inside triggers, opening transform and toggle button.
- Stores captured pieces.
- Exposes `TotalPieceCount`, `CurrentStoredPieceCount` and optional `TMP_Text pieceCountLabel` with format `{CURRENT} / {TOTAL}`.
- Shows `BoxGlowTape` only after the close animation has fully reached the `Closed` animator state; opening hides it immediately. It replaces the old hover `HighlightPlane` and uses `Box Glow Tape.mat` / `Glow Strip Unlit` for a moving shimmer.
- Shows an intake preview line from held piece to the box while hovering over an open capture trigger, and keeps it during capture until storage completes.
- Uses `openingDirectionLocal` as the outward hole direction and `[TRIGGER] PourSpawnPlane` as the preferred random spawn plane for pouring; old generated prefabs fall back to `BoxTriggerInside`.
- Open-box pour rate and impulse are angle-driven from `startPourAngleFromDown` to `fullPourAngleFromDown`, with inspector min/max pieces per second, min/max impulse, max pieces per frame, impulse spread, collision-ignore duration and `pourScaleRestoreDelay`. Poured pieces spawn shrinked and grow back after the restore delay.
- Pouring only emits from a shuffled queue of `storedPieces`; pieces are removed from storage, reactivated, yaw-randomized, gravity/non-kinematic restored and pushed outward.
- Held open boxes auto-tilt above placement surfaces only when `WorldInteraction_Drag_Object.IsHeld` is true and a downward raycast hits `PuzzlePlacementAreaMask`; auto-tilt preserves player yaw/azimuth.
- Selected gizmos draw the opening vector and spawn volume.
- Applies image/preview materials and completed/incomplete visual state.
- APIs:
  - `AutoWire`
  - `BindLevelState`
  - `SetPuzzleVisualState`
  - `SetOpen`
  - `IsOutsideTrigger`
  - `IsLidCollider`
  - `TryCapturePiece`
  - `ApplyPuzzleMaterials`

`PuzzleBoxInteractionService.cs`
- Used by `WorldInteraction_Hand_InputController`.
- Checks box capture before placement-area release.
- Downward raycasts held pieces into `BoxTriggerOutside`.
- Forces `PuzzlePieceDragScaleController` shrink while held over an open box and keeps the intake preview line visible before release.
- Requests `PuzzleBoxController.ShowCapturePreview` while hover target is valid and clears it when the piece leaves.

`PuzzleBoxTrigger.cs`
- Marks outside/inside trigger kind.

`PuzzleBoxToggleButton.cs`
- Inherits `WorldInteraction_Toggle_Button`.
- Implements `IHandUsable` and `IHandHoverable`.
- Calls `PuzzleBoxController.SetOpen(bool)`.

`PuzzlePieceDragScaleController.cs`
- Scales held pieces along X/Z for drag/box interactions.
- Supports forced shrink sources.
- Shrink is box-only by default: `allowPuzzleBoxInOutShrink = true`, min X/Z scale is `0.4`, max X/Z scale is `1`, and normal pickup/release/idle does not change scale.
- Legacy default min value `0.82` and the temporary scale-off min value `1` normalize to box shrink min `0.4`; `0.4` remains valid.
- A placed puzzle piece must always resolve to max scale; `ApplyMaxScaleImmediate()` is called after placement-area placement.

`PuzzlePieceDragScaleSetup.cs`
- Collects piece scale controllers under pieces root and applies global/per-piece settings.

WorldInteraction bridge for physical box pickup:
- `Assets/Runtime/WorldInteractionBridge/WorldInteraction_Hand_DraggableBridge.cs`
  - Bridges hand system to generic `WorldInteraction_Drag_Object`.
  - Supports whole-object pickup.
  - Uses `WorldInteraction_Drag_LiftUtility` only for box bottom clearance while `WorldInteraction_Drag_LiftUtility.ObstacleLiftGloballyEnabled` is false.
  - Assigns model bounds to `ModelBounds` layer and ignores collisions.
- `Assets/Runtime/Hand/WorldInteraction_Drag_LiftUtility.cs`
  - Contains the disabled bounds/footprint obstacle lift prototype. It can raise held grip targets over obstacles using `modelBoundsCollider`, non-trigger child colliders, or renderer bounds when `ObstacleLiftGloballyEnabled` is re-enabled.
  - Default obstacle mask is `PuzzlePlacementArea | Table | PuzzleBox | PuzzlePiece`; self colliders, triggers, `ModelBounds`, and `BoxToggle` are ignored, but active stored/capturing pieces are not children of the held box and can cause jitter if `PuzzlePiece` remains in the box obstacle mask.

Important ModelBounds rule:
- `ModelBounds` is service-only.
- Do not include `ModelBounds` in interaction masks.
- Do not use ModelBounds collider for hover, pickup, toggle, physical contacts or placement.

## 21. Current Gameplay Flow

Startup:
1. `Assets/Scenes/Main.unity` starts first.
2. `AppManager` loads configured additive scenes.
3. Template managers initialize through singleton/stage flow.
4. Game scene provides `PixelVoxelPuzzleGameRoot` and scene-specific systems.
5. `PuzzleAutoStartup` may start a default puzzle if configured.

Input:
1. Template `InputManager` detects key/mouse input.
2. `InputContextRouter` checks current `PixelVoxelPuzzleInputContext`.
3. Router sends commands to hand, camera, swing or physical menu.

Level selection:
1. Player uses `World3DLevelButton`.
2. `UILevelSelectModule.SelectPuzzleIndex` checks lock state and puzzle library.
3. Existing session on the target BoardArea is packed if needed.
4. `PuzzleSessionManager.StartSession` builds the selected puzzle on its BoardArea.
5. `GroundPivotFastTravelController` can move the camera pivot to the active BoardArea.

Puzzle session:
1. `PuzzleSessionFactory` resolves BoardArea and spawns pieces/optional box.
2. Pieces are held through `WorldInteraction_Hand_Controller` and `PuzzlePieceHoldable`.
3. `PuzzlePlacementService` previews and validates placement.
4. `PuzzlePlacementArea` writes occupancy.
5. `PuzzleCompletionService` checks target completion.
6. `PuzzleSessionManager` raises completion/placement events.

Save:
1. `PixelVoxelPuzzleSaveController` captures level/session/piece state.
2. It integrates with Template `SaveManager` through `PixelVoxelPuzzleSaveItem`.
3. Save data restores level button states and active session if configured.


## 22. Scene Hierarchy Rules

Preferred Game hierarchy:

```text
Game
  Systems
  World
  Runtime
  _Debug
```

`Systems`
- Logic only:
  - input
  - hand
  - interaction/swing
  - puzzle session
  - camera system
  - UI manager modules
  - save bridge
  - recovery

`World`
- Hand-authored world content:
  - environment
  - level select
  - board areas
  - physical menu
  - world UI
  - achievement gallery
  - secrets
  - puzzle boxes if authored/generated as world objects

`Runtime`
- Spawned/controlled runtime content:
  - `ActivePuzzleSession`
  - pieces
  - placement preview
  - generated objects
  - pool

`_Debug`
- Temporary test/debug objects.
- If deleting `_Debug` breaks normal play, the architecture is wrong.

Current important BoardArea structure:

```text
BoardArea_Main
  PlacementArea
  ContainmentArea
  SessionPieces
  SessionBox
  Effects
  BoxSpawnAnchor
  BoxPreviewAnchor
  Buttons
```

## 25. AI Editing Guidelines

Before changing architecture:
- Read the relevant README/doc and the actual class implementation.
- Check whether the behavior belongs in Template generic code or PixelVoxelPuzzle project code.
- Use bridges for project-specific behavior.
- Keep Main-scene singleton managers unique.
- Keep Game-scene systems under `Systems`, authored objects under `World`, spawned objects under `Runtime`, temporary objects under `_Debug`.

When changing input:
- Do not put puzzle rules into `InputManager`.
- Use `InputContextRouter`, `InputContextStack`, `WorldInteraction_Hand_InputController`, camera bridge or physical menu navigator.

When changing camera:
- Prefer `DanieloZ.CameraSystem`.
- Do not add direct key reads to camera module classes.
- Route input through PixelVoxelPuzzle input bridge/router.

When changing world interaction:
- Generic reusable interaction goes under `Assets/Template/Modules/DanieloZ.WorldInteraction`.
- PixelVoxelPuzzle-specific rules go under `Assets/Runtime/WorldInteractionBridge` or feature-specific runtime folders.

When changing screen-space outlines:
- Generic RenderFeature, shaders and material profiles belong in `Assets/Template/Modules/DanieloZ.ScreenSpaceOutline`.
- Keep object selection and layer-switching rules in project-side runtime code.
- Prefer grouping layers under shared feature instances because every additional feature adds mask and composite passes.
- Preserve the RenderFeature script GUID and assembly identity when moving or restructuring it.

When changing puzzle placement:
- Grid placement and occupancy logic belongs in `PuzzlePlacementArea`.
- BoardArea world wiring belongs in `BoardAreaController`.
- Candidate/validation/release coordination belongs in `PuzzlePlacementService`.
- Visual lines belong in `PuzzlePlacementPreviewView`.
- Held-object behavior belongs in `PuzzlePieceHoldable`.
- Completion target checks belong in `PuzzleCompletionService`.

When changing Level Select:
- `UILevelSelectModule` owns selection/progression-facing state.
- `World3DLevelButton` is the physical view.
- Do not make level buttons spawn puzzle pieces directly.

When changing save:
- PixelVoxelPuzzle capture/apply logic belongs in `PixelVoxelPuzzleSaveController`.
- Serializable data belongs in `PixelVoxelPuzzleSaveData`.
- Integration with global persistence goes through Template `SaveManager` and `SaveItem`.

When changing generated scenes:
- Prefer updating `PixelVoxelPuzzleGameSceneGenerator.cs` if the scene is meant to be reproducible.
- Be careful: generator can rebuild/overwrite `Assets/Scenes/Game.unity`.
- Preserve existing Bezier curve data if camera curves are user-tuned.

When changing puzzle generation:
- `PixelPuzzleGeneratorController.cs` is large and owns many responsibilities.
- Use `PixelPuzzleGeneratorWindow` and custom editor only for editor UX.
- Keep baked runtime data in `PixelPuzzleAsset`, `PixelPuzzlePieceData`, `PhysicsShapeData` and generated meshes/materials.

When touching dirty working tree:
- Do not revert user changes.
- Check `git status --short`.
- Touch only files required by the task.
